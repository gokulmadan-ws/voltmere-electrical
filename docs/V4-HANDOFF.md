# V4: a real cross-device loop with no server (WhatsApp link handoff)

Problem: the prototype stores everything in one browser's localStorage, so a booking made on a customer's phone never reaches Daniel's phone, and a quote link texted to a customer says "not valid on this device". A server would fix it; a static prototype cannot have one. But WhatsApp deep links ARE a real transport that needs no server, and Daniel lives in WhatsApp. So the loop becomes REAL across two phones, with the customer tapping "send" themselves:

1. Customer finishes the funnel on THEIR phone. The confirmation offers "Send my enquiry to Daniel on WhatsApp": a real `https://wa.me/447885496800?text=...` link whose text lists the enquiry in plain words and ends with a link `dashboard.html#import=<payload>`. (In a real build his webhook does this silently; here it is the transport. Tag the button as a prototype idea: `data-proto`.) It also stays saved in the customer's own browser as today.
2. Daniel taps that link in WhatsApp on HIS phone. His dashboard opens an "Import enquiry" screen showing exactly what the customer entered (name, mobile, postcode, answers, notes, source) and a button "Add to my dashboard". It creates the enquiry in HIS store (with the 24 hour reply clock, suggested survey slot from HIS diary, simulated alert), idempotent: tapping it twice never duplicates.
3. Daniel builds and sends a quote. The quote link now carries the quote itself: `quote.html#d=<payload>` (compact JSON, base64url, no server). It renders on ANY phone. When the quote exists in the viewer's own store (same browser) the page behaves exactly as today.
4. The customer opens the link on their phone, reads the quote and taps "Accept quote". Because their phone has no copy of Daniel's diary, the install-day picker is replaced (in link mode) by "Which days suit you?" chips (weekday chips Mon..Sat, plus Morning / Afternoon / Any) and an optional note. Accept opens a real WhatsApp message to Daniel: "I'd like to go ahead with quote Q-EL-1043 (£1,394). Best: Thu or Fri mornings. <link to dashboard.html#import=<acceptance payload>>". Decline similarly, with the reason chip.
5. Daniel taps that link: the Import screen shows "Aoife accepted quote Q-EL-1043 (£1,394), prefers Thu/Fri mornings" with "Mark quote accepted and plan the install". That marks the quote accepted in HIS store and creates an unscheduled install booking (status new, "To be arranged", the preferences in its notes), which appears in the pipeline under Accepted with the "Confirm the install day" action.

All payloads are plain data in a URL fragment (never sent to any server; GitHub Pages never sees them). They are UNTRUSTED input: strict validation, length limits, no HTML, tolerant of garbage, and the receiving screen always shows what will be imported and requires a tap.

## Payload format (js/core/handoff.js, role A4)

`encodePayload(obj)` -> base64url of compact JSON (UTF-8 safe; no padding). `decodePayload(str)` -> object or `null` (never throws). Every payload: `{ v: 1, t: 'enq'|'quo'|'acc'|'dec', ... , k: <6 char checksum of the rest> }`; a wrong checksum or version is `null`. Keep payloads small (an enquiry under ~900 characters encoded, a quote under ~1,800).
- `enq` (enquiry): `i` ref (EL-1043), `c` created stamp ('YYYY-MM-DDTHH:mm'), `n` name, `p` mobile, `e` email, `z` postcode, `a` { parking, vehicle, timing, permission } (stored values), `o` marketing opt-in (0/1), `m` notes (max 400 chars), `u` utm source id.
- `quo` (quote): `i` quote id (Q-EL-1043), `r` enquiry ref, `n` customer first name, `z` postcode, `b` brand, `l` lines [[label, qty, unitPrice], ...] (max 14), `m` notes (max 400), `x` valid-until day key, `s` sent stamp, `f` flags (bit 1: sample prices).
- `acc` (acceptance): `i` quote id, `n` name, `d` days chips (subset of mon..sat), `w` 'am'|'pm'|'any', `m` note (max 200), `t2` total (for display, re-checked on import).
- `dec` (decline): `i` quote id, `n` name, `y` reason id.

## Core API (role A4; document in docs/V4-API.md first)

- `js/core/handoff.js`: `encodePayload`, `decodePayload`, `buildEnquiryPayload(booking)`, `buildQuotePayload(quote, booking)`, `buildAcceptancePayload({ quote, days, part, note })`, `buildDeclinePayload({ quote, reason })`, `enquiryWhatsAppText(booking, { link })`, `acceptanceWhatsAppText(...)`, `declineWhatsAppText(...)`, `dashboardImportLink(payload)`, `quoteLink(quote)` (the self-contained `quote.html#d=` link built from SITE_BASE_URL), `parseImport(hashOrString)` -> `{ ok, kind, data } | { ok:false, reason }`.
- Store: `importEnquiry(payload)` (validates; creates the booking exactly like a website enquiry with source 'website' + the payload's utm, createdAt from the payload (clamped to not be in the future), answers, customer, notes, `importId` = the ref; idempotent: same ref again returns `{ ok:true, existed:true, bookingId }`), `importQuoteDecision(payload)` for `acc` and `dec` (finds the local quote by id; if missing returns `{ ok:false, reason:'quote_not_found' }` with a friendly explanation; accepted: marks accepted with `acceptedVia:'whatsapp'`, creates the unscheduled `ev` booking with preferences in notes, idempotent; declined: marks declined). `sendQuote` now builds its link with `quoteLink(quote)` (the self-contained one) so messages carry it. Everything returns `{ ok, ... }` like the rest of the store; unit tests for every path, hostile input (huge strings, wrong types, HTML, bad checksums, future dates, duplicate import).
- Existing same-browser behaviour is unchanged.
